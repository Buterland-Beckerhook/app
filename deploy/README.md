# Deployment (Beta & Prod)

The container is built by **GitHub Actions** and pushed to **GHCR**
(`ghcr.io/buterland-beckerhook/app`). The server **does not build** — it only pulls
the finished image. The image is **multi-arch (`linux/amd64` + `linux/arm64`)**; the
prod server is arm64/v8.

- Build workflow: `.github/workflows/build.yml` — runs on push to **`main`**, weekly
  (Monday 04:17 UTC, a cache-free rebuild of the runtime stage so Debian security
  updates land even without a commit) and via "Run workflow" (workflow_dispatch).
  Tags: `:beta` (rolling), `:YYYYMMDD-HHMM-<sha>` (immutable build tag, UTC) and
  `:sha-XXXXXXX` (the newest build of that commit — moves on a rebuild).
  **Beta tracks `main`; Prod pins a build tag.**
- A single `docker compose` stack (`deploy/compose.yml`) serves **Beta and Prod** — the
  difference lives entirely in `.env` (`STACK_NAME`, `IMAGE`, `PHX_HOST`, `TRAEFIK_NAME`,
  `TRAEFIK_RULE`, `TRAEFIK_MIDDLEWARES`, `BASIC_AUTH_USERS`), all generated by `setup.sh`.
  `STACK_NAME` is the Compose project name and thus the named-volume prefix
  (`bbh-beta_*` vs `bbh-prod_*`), so both stacks coexist on one host with separate data.

> Building before the rewrite has merged: the push trigger only fires on `main`, so
> until then build ad-hoc via **GitHub → Actions → Build & push image → Run workflow**
> against your branch.

## Reverse proxy: central Traefik

The stack ships **no reverse proxy of its own** and publishes **no ports**. TLS
(Let's Encrypt), the HTTP→HTTPS redirect, compression, the `www`→apex redirect (Prod)
as well as Basic-Auth + `noindex` (Beta) are all handled by the **central Traefik** on
the host, driven by Docker labels on the `phoenix` service (see `compose.yml`).

Prerequisites: the external Traefik network **`proxy`** already exists on the host, and
Traefik knows the referenced file-provider building blocks `https-redirect@file`,
`secure-tls@file` and the certresolver `le`. (Both are already the case in the existing
setup.)

The `proxy` network **must have IPv6** (done 2026-10-29):

```bash
docker network create --ipv6 --subnet 172.18.0.0/16 --subnet fd42:abcd:1::/64 proxy
```

Without it, Docker has no IPv6 NAT rule for Traefik's ports and hands IPv6 clients to
Traefik through `docker-proxy`, which replaces the client address with the network's
gateway (`172.18.0.1`). The app then sees one address for every IPv6 visitor: the rate
limit buckets them together, and the login log and the membership submission record
store the gateway instead of the client (`BbhWeb.ClientIp`). mailcow's nginx sits on the
same network, so its login protection is affected the same way.

## First-time setup on the server

1. **DNS:** A record (`beta.buterland-beckerhook.de` for Beta) → server IP. Ports
   80/443 are already served by the central Traefik — this stack opens none itself.

2. **Get the `deploy/` folder onto the server** (git clone the repo or copy the folder).

3. **Generate `.env` with the setup script** (from inside `deploy/`):
   ```sh
   ./setup.sh          # interactive; or: ./setup.sh --yes   (accept generated defaults)
   #                     ./setup.sh --prod  presets prod-mode defaults (default is beta)
   ```
   The script is **idempotent** — re-running only fills values that are still missing;
   existing values are preserved. It:
   - generates every secret **locally with `openssl`** — `SECRET_KEY_BASE`, the
     **VAPID** keypair (Web Push), `ALTCHA_HMAC_KEY`, and a URL-safe `DB_PASSWORD`.
     No image or Mix is needed, so there is **no ordering dependency** on the GHCR pull.
   - for Beta, offers **Basic-Auth**: enter a username (or accept `beta`) and a password
     (or let it generate one — printed **once**, save it). It hashes with bcrypt and
     writes the value **`$`-escaped** so Compose interpolation keeps the hash intact.
   - sets `TRAEFIK_*` from the chosen mode/host and writes `.env` with `chmod 600`,
     then self-checks it with `docker compose config`.
   - You are prompted for the rest (hostname, SMTP, …) with sensible defaults.

   > **Do not hand-edit secrets or the auth hash.** If you must edit `.env` by hand,
   > remember every literal `$` has to be doubled to `$$` (Compose interpolates `.env`
   > values). This is exactly why Basic-Auth failed silently before. Re-run `setup.sh`
   > rather than editing.

4. **Access the image on GHCR** (the package is private by default) — either log in once
   with a fine-grained PAT that has `read:packages`:
   ```sh
   echo <PAT> | docker login ghcr.io -u <github-user> --password-stdin
   ```
   or set the GHCR package to **public** in its settings (the image holds no secrets —
   those come at runtime from `.env`), which removes the login step. Make sure the
   `:beta` image exists (push to `main`, or run the workflow via workflow_dispatch).

5. **(Optional) seed data — see [Restoring a dump](#restoring-a-dump).** Drop a backup
   into `deploy/restore/` before the first `up` to launch with real content.

6. **Start the stack:**
   ```sh
   docker compose --env-file .env up -d
   ```
   Postgres comes from the public image, Phoenix from GHCR. On boot: the one-shot
   `restore` step runs (a no-op unless `restore/` holds a dump), then Phoenix runs
   `bin/migrate` and starts the server. Traefik picks up the new container from its labels.

### Verify success

```sh
docker compose --env-file .env ps                             # all services "healthy"
curl -fsS https://beta.buterland-beckerhook.de/health/liveness # 200 (once TLS is issued)
```
In the browser: the Basic-Auth dialog (Beta), then the home page renders. Admin login
at `/users/log-in`.

On Beta the app itself also keeps crawlers out and marks the site, independent of the
Traefik `noindex` middleware (`BbhWeb.Beta`): every response carries `X-Robots-Tag`,
`/robots.txt` disallows everything (AI crawlers by name), and every page shows a
„Beta-Version“ banner at the top and bottom linking the same page on the live site. It
switches on by itself for a `beta.` `PHX_HOST`; `BETA=true` in `.env` forces it for
any other host.

## Restoring a dump

The stack can restore a backup automatically on boot. Anything dropped into
`deploy/restore/` is picked up by the one-shot `restore` service **before** Phoenix
starts (Phoenix then migrates on top, so a slightly older dump is still brought
up-to-date):

**Initial seed** (fresh stack, before the first `up`):
```sh
cp bbh-2026-07-16.dump        deploy/restore/     # DB (pg_dump -Fc, from backup.sh)
cp uploads-2026-07-16.tar.gz  deploy/restore/     # optional: uploaded originals
docker compose --env-file .env up -d
```

**Re-seed a running deployment** — ⚠️ stop Phoenix first. The restore `--clean`s the
DB, which would fight (or corrupt) a live app still holding connections:
```sh
docker compose --env-file .env stop phoenix
cp bbh-2026-07-16.dump deploy/restore/
docker compose --env-file .env up -d            # restore runs, then Phoenix restarts
```

- Restore runs **only when a `*.dump` is present**; on success **every** dump/uploads
  file is renamed to `*.restored`, so restarts never re-restore. Drop a fresh `*.dump`
  in to restore again. Keep to **one dump at a time** — the newest is used.
- ⚠️ **Destructive:** restoring `--clean`s and overwrites the current database.
  Intended for (re)seeding — not an "apply diff".
- A failed restore keeps Phoenix down (rather than serving a half-restored DB); check
  `docker compose --env-file .env logs restore`.

## Update flow ("practice")

Merging to `main` (including Renovate's auto-merges) builds a fresh image. From there:

- **Beta updates itself** every hour through a systemd timer, so it is the first to run
  every build — set it up once per host:
  ```sh
  sudo install -m 0644 systemd/bbh-update@.service systemd/bbh-update@.timer /etc/systemd/system/
  sudo systemctl daemon-reload
  sudo systemctl enable --now "bbh-update@$(systemd-escape -p /path/to/beta/deploy).timer"
  journalctl -u "bbh-update@*" --since today      # what it did
  ```
  Each run is a plain `./update.sh`: `git pull`, `compose pull`, `up -d` — a no-op when
  nothing changed.
- **Prod is updated by hand**, once Beta looks fine:
  ```sh
  sudo ./update.sh --latest
  ```
  It looks up the newest build tag on GHCR, shows the GitHub compare link, asks, takes
  a safety dump into `backups/pre-update-*.dump` (last 5 kept), rewrites `IMAGE` in
  `.env` and restarts. Migrations run on boot.

Security fixes: Renovate assigns its vulnerability PRs, so GitHub notifies about each
one. It still auto-merges a patch — the notification is the cue to deploy Prod.

Prod deliberately does not deploy itself: a migration runs unattended on boot, and a
broken one is not undone by going back to the old image — only by restoring the dump.

### Rollback

`update.sh` prints the previous tag after every switch. Older build tags are listed on
GHCR (or in the Actions log).
```sh
sudo ./update.sh --tag 20261020-0417-abc1234
```
That only swaps the image. If the newer image already migrated the database, restore the
safety dump together with it — the `restore` service runs before Phoenix boots (see
[Restoring a dump](#restoring-a-dump)):
```sh
sudo docker compose --env-file .env stop phoenix
sudo cp backups/pre-update-20261026-091500.dump restore/
sudo ./update.sh --tag 20261020-0417-abc1234
```

## Logs & shutdown

```sh
docker compose --env-file .env logs -f phoenix     # follow app logs
journalctl -t bbh-prod-phoenix-1 --since today     # same, straight from the journal
```

- **Retention: 30 days.** All services log through Docker's `journald` driver (the
  `x-logging` anchor in `compose.yml`), because the logs contain personal data (e.g.
  recipient addresses of sent mail) and the privacy policy promises at most 30 days.
  Docker's default `json-file`/`local` drivers can only rotate by size, so they cannot
  guarantee an age limit; journald can. Set it up **once per host**:

  ```sh
  sudo install -D -m 0644 journald-bbh.conf /etc/systemd/journald.conf.d/bbh.conf
  sudo systemctl restart systemd-journald
  docker compose --env-file .env up -d          # recreate the containers with the new driver
  ```

  `journald-bbh.conf` sets `MaxRetentionSec=30day` and `MaxFileSec=1day`. The second
  matters: journald only deletes whole journal files once their newest entry is past
  the limit, and with the default monthly rotation entries could survive up to a month
  longer. The setting applies to the whole host journal. Check that the drop-in is
  active with `systemd-analyze cat-config systemd/journald.conf`, and see the oldest
  kept entry with `journalctl -t bbh-prod-phoenix-1 -o short-iso | head -n 2`.
  Recreating a container drops its old `json-file` log together with the container.
  Other stacks on the host (mailcow, Traefik) keep their own logging config — check
  them separately.

- **Log level** is set by `LOG_LEVEL` in `.env` — any Elixir Logger level
  (`debug|info|notice|warning|error|critical|alert|emergency`), default `info`.
  The frequent `/health/*` container/proxy probes are logged at
  `debug`, so they stay out of the logs at the default level. To include them (and
  everything else) while diagnosing, set `LOG_LEVEL=debug` and re-`up` phoenix.
- **Time zone** is set by `TIME_ZONE` in `.env` (IANA name, default
  `Europe/Berlin`). It drives event/article wall-clock times (`Bbh.Time`), the
  iCal `TZID`, and the container's OS zone (`TZ`, so log timestamps are local).
  The bundled `VTIMEZONE` encodes Central European (CET/CEST) DST rules, so only
  CET zones are emitted in iCal correctly without further code changes.
- **Graceful shutdown:** on `down`/restart the app receives `SIGTERM` and drains
  in-flight requests (Bandit, up to 55s) before exiting — well inside the 60s
  `stop_grace_period`. A `down` that instead sits for the full 60s and is then
  killed means the signal isn't reaching the BEAM (PID 1); keep the `exec` in the
  compose `command` so it does.

## Prod

Run `./setup.sh --prod` for its own `.env`. Prod defaults differ from Beta:
- `STACK_NAME=bbh-prod` (Beta uses `bbh-beta`) — distinct project name and volumes
  (`bbh-prod_pgdata` / `bbh-prod_uploads`).
- `PHX_HOST=buterland-beckerhook.de`, `TRAEFIK_NAME=bb`,
  `TRAEFIK_RULE=Host(\`buterland-beckerhook.de\`, \`www.buterland-beckerhook.de\`)`,
  `TRAEFIK_MIDDLEWARES=bb-compress,bb-www` (compression + www→apex redirect, **without**
  Basic-Auth/noindex).
- Pin `IMAGE` to a build tag (`:YYYYMMDD-HHMM-<sha>`) — `./update.sh --latest` does it
  for you, so setup.sh's `:beta` default is fine for the first start.

Beta and Prod run on the same Traefik — so they use **different `TRAEFIK_NAME`s**
(`bb-beta` vs. `bb`), otherwise router/middleware names collide.

## Syncing Prod data to Beta

`deploy/sync-data.sh` copies the database **and** the uploads of one stack into another
on the same host — typically to test a new feature on Beta against current Prod content:

```sh
./sync-data.sh --from /path/to/prod/deploy --to /path/to/beta/deploy
```

- Prod keeps running (`pg_dump` reads one consistent snapshot); only Beta's Phoenix is
  stopped while its DB is dropped, restored (single transaction) and its uploads volume
  replaced. Beta then boots and migrates on top, so a Beta image with newer migrations
  just applies them.
- Before overwriting, a safety dump of the target goes to `<target>/backups/`
  (last 5 kept).
- **Sanitized on the target:** `push_subscriptions` (a test publish must never reach
  real subscribers), `users_tokens`, `api_tokens`, `oauth_*` and `oban_*` (queued pushes
  and reminders) are emptied. Users, content, media and settings are kept.
- Log in on Beta afterwards via **magic link** — passkeys are bound to the host name and
  do not carry over. An MCP client connected to Beta must re-authorize.
- Guards: refuses identical stacks and any target whose `PHX_HOST` is not `beta.*`
  unless `--allow-prod-target` is given; asks you to type the target host (`--yes` skips
  that, e.g. for cron). `--no-uploads` syncs the DB only.

## Backups (Prod → Hetzner Storage Box)

`deploy/backup.sh` runs nightly as root and writes two encrypted, deduplicated Borg
archives per night: `bbh-prod-db-DATE` (the `pg_dump -Fc`) and `bbh-prod-uploads-DATE`
(the uploaded originals; variant cache and map archive are regenerable and skipped).
Retention: 7 daily, 4 weekly, 6 monthly. The last 3 dumps also stay in
`/var/backups/bbh` for a quick restore. Only Prod is backed up — Beta is refilled from
Prod with `sync-data.sh`.

### One-time setup

1. **Storage Box:** in the Hetzner console create a **sub-account** for this backup
   (own login, own base directory, so it cannot touch other repos on the box, e.g.
   mailcow's) with *SSH support* and *External reachability* enabled. Borg runs over
   port **23**; below, `uXXXXXX-subN` is that sub-account.
2. **Borg on the host:** `apt install borgbackup` (`borg --version`; 1.2 or newer).
3. **SSH key** for root, used only for the backup:
   ```sh
   ssh-keygen -t ed25519 -N '' -f /root/.ssh/bbh-backup -C bbh-backup
   cat /root/.ssh/bbh-backup.pub | ssh -p 23 uXXXXXX-subN@uXXXXXX.your-storagebox.de install-ssh-key
   ```
4. **Config** `/etc/bbh-backup.env` (`chmod 600`, owned by root):
   ```sh
   BORG_REPO=ssh://uXXXXXX-subN@uXXXXXX.your-storagebox.de:23/./bbh-borg
   BORG_PASSPHRASE=<openssl rand -base64 32>
   BORG_RSH="ssh -i /root/.ssh/bbh-backup -o BatchMode=yes"
   BORG_REMOTE_PATH=borg-1.4   # the Storage Box offers several; match the host's major.minor
   HC_PING_URL=https://hc-ping.com/<uuid>
   ```
5. **healthchecks.io:** create a check with period *1 day* and grace *2 hours*, and
   paste its ping URL above. The script pings `/start`, success, or `/fail` with the
   log tail — and a night without any ping alerts too (cron dead, host down).
6. **Create the repo** — and store the passphrase **and** the printed key in the
   password manager. The key lives in the repo too, but if the box is lost or the
   passphrase forgotten, the backup is unreadable:
   ```sh
   ./backup.sh init
   ```
7. **First run by hand**, then check the archives:
   ```sh
   ./backup.sh
   set -a; . /etc/bbh-backup.env; set +a; borg list
   ```
8. **Cron** (`crontab -e` as root):
   ```
   15 3 * * *  /path/to/prod/deploy/backup.sh >> /var/log/bbh-backup.log 2>&1
   ```

### Restore

```sh
set -a; . /etc/bbh-backup.env; set +a
borg list                                              # pick a date
cd /path/to/prod/deploy/restore
borg extract    ::bbh-prod-db-2026-10-24               # -> bbh-2026-10-24.dump
borg export-tar ::bbh-prod-uploads-2026-10-24 uploads-2026-10-24.tar.gz
cd .. && docker compose --env-file .env stop phoenix && docker compose --env-file .env up -d
```

The archives are laid out exactly as the `restore` service expects (see
[Restoring a dump](#restoring-a-dump)). For a quick DB-only rollback, copy one of the
local dumps from `/var/backups/bbh` instead. Do **not** restore a Prod backup into
Beta: unlike `sync-data.sh` it is not sanitized, so Beta would hold the real push
subscriptions and queued Oban jobs.

## Postgres major upgrade (16 → 18)

The stack runs **Postgres 18**. Stacks set up on 16 keep their data in the volume
`${STACK_NAME}_postgres_data`, which an 18 server cannot open; the 18+ image also moved
its layout (volume at `/var/lib/postgresql`, `PGDATA=/var/lib/postgresql/18/docker`).
The data therefore moves **once**, by dump & restore, into a new volume
`${STACK_NAME}_pgdata`. The legacy volume is only ever read — it is the rollback path.
Background: [ADR 0012](../docs/adr/0012-postgres-major-upgrade-by-dump-and-restore.md).

**Order: Beta first, then Prod.** An 18 dump cannot be restored into 16, so
`sync-data.sh` only works while the target is on the newer major.

```sh
cd /path/to/beta/deploy
git pull --ff-only          # brings in compose.yml + upgrade-postgres.sh (do NOT run update.sh yet)
./upgrade-postgres.sh       # asks you to type the host; --yes skips that
```

What it does (details in `./upgrade-postgres.sh --help`): stops the stack, dumps the
database from a throwaway `postgres:16-alpine` on the legacy volume (also kept in
`backups/pg16-final-*.dump`), lets the new 18 server and the `restore` service load it,
**compares the exact row count of every table**, then starts the whole stack and waits
for Phoenix to turn healthy. Any failure leaves Phoenix **down** and the legacy volume
untouched. Downtime is about a minute or two.

Then test on Beta (log in, edit and save an article, upload an image, run
`./sync-data.sh --from <prod> --to <beta>` once) and repeat the upgrade for Prod.

- **Forgot the script?** An `update.sh` / `up -d` with the new `compose.yml` starts 18 on
  an empty new volume. The `restore` service notices the legacy cluster and refuses to
  continue, so Phoenix stays down instead of serving an empty site. Just run
  `./upgrade-postgres.sh` — it clears that empty volume and carries on.
- **Rollback** (before anything was written on 18, or accepting the loss of such writes —
  an 18 dump does not restore into 16): `git checkout <previous commit> -- compose.yml
  restore-entrypoint.sh && docker compose --env-file .env up -d`. The 16 server comes up
  on the untouched legacy volume.
- **Cleanup** once the new database has proven itself (a few days):
  `docker compose --env-file .env rm -f restore && docker volume rm ${STACK_NAME}_postgres_data`.
  Compose re-creates it empty on the next `up`; the `restore` tripwire ignores an empty one.
- **Dev:** the dev stack uses the new volume `pgdata`; the old `pg_data` is simply no
  longer mounted. To keep your dev data: `make dump` **before** pulling this change,
  then `make dev` and `make seed`. Remove the old volume with
  `docker volume rm app_pg_data` (name depends on your checkout directory).

## Event map archive

The embedded map on event pages is served from `/data/map/region.pmtiles` in the
uploads volume. The app fetches it by itself: once after the first boot, then monthly,
and whenever a venue outside the covered area is saved (needs outbound HTTPS to
`build.protomaps.com`; the extract is ~10 MB). Watch for `[map]` lines in the log. To
force a refresh:

```sh
docker compose --env-file .env exec phoenix bin/bbh rpc "Bbh.Map.enqueue_update()"
```

Until an archive exists, event pages simply show the address and OpenStreetMap links.
`MAP_TILES_FILE=/data/…` pins a hand-made archive instead (the updater then leaves it
alone). The archive is regenerable and not part of the backup. See
[ADR 0014](../docs/adr/0014-self-hosted-osm-map.md).

## Backups

`deploy/backup.sh` — nightly `pg_dump` + uploads, offsite via Borg (cron as root). To
restore one of its archives, copy the `.dump` (and `uploads-*.tar.gz`) into
`deploy/restore/` and run `docker compose up -d` — see [Restoring a dump](#restoring-a-dump).
